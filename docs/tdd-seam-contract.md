# P4 — TDD Seam Contract (Task/Workflow execution)

## Scope

P4 is an opt-in extension of the existing Task/Workflow execution contract. It is
not a standalone TDD Skill. Tasks without a declared seam keep the legacy
checkpoint behavior.

A seam may be declared directly on a Task step or inherited from a Workflow
Template step with `tdd_test_command`.

## Declaration

At Task creation, a TDD step freezes:

- `test_command`
- `declared_at`

The declaration timestamp is generated by the Task state layer and cannot be
replaced by checkpoint evidence. A completion checkpoint must prove executions
that started after this declaration.

## Executor receipts

Completed `exec_command` / observed command sessions issue a durable receipt
under `$AGENTDOCK_HOME/execution-receipts`. The public command result exposes
only an `execution_receipt.ref` such as `exec://session-...` plus compact
metadata.

Each persisted receipt binds:

- executor issuer and session id
- exact normalized requested command and command SHA-256
- process exit code and terminal status
- start and finish timestamps
- runtime and working directory
- SHA-256 of the full stdout and stderr streams
- an integrity SHA-256 over the receipt payload

Output digests are computed over the complete streamed output before bounded
command buffers are trimmed. Raw stdout/stderr are not duplicated into the
receipt store, avoiding a second long-lived copy of potentially sensitive logs.

## Completing a seam

A TDD step is completed with a **single-step** checkpoint. The caller supplies
only executor receipt references:

```json
{
  "tdd_seam": {
    "red_ref": "exec://session-...",
    "green_ref": "exec://session-...",
    "regression_ref": "exec://session-..."
  }
}
```

The Task service resolves the receipts itself and fails closed unless all of the
following are true:

1. all three receipts exist and pass their integrity check;
2. all three were issued by `agentdock.exec_command/v1`;
3. all three execute the frozen command and command digest;
4. all runs start after the seam declaration;
5. all runs finish normally and are not timeouts/killed executions;
6. Red exits nonzero;
7. Green and Regression exit zero;
8. the receipts are distinct;
9. Red finishes before Green starts;
10. Green finishes before Regression starts.

Caller-supplied command strings, exit codes, timestamps, or executor identities
are not accepted as TDD evidence.

## Single-use and atomicity

Receipt references are durably claimed by `task:<task_id>:step:<step_id>`.

- A receipt already claimed by another task/step is rejected.
- Reusing the same receipt in multiple TDD phases is rejected.
- A retry for the same task/step remains idempotent.
- Claims created for a checkpoint are rolled back if receipt verification or
  the Task state transition fails.
- Invalid evidence does not mutate the Task step.
- Batch checkpoints cannot bypass an incomplete TDD-declared step.

## Workflow propagation

`TemplateStep.tdd_test_command` is copied into the concrete Task step when a
Task is created from an active Workflow Template. The Task state layer then
creates the same immutable declaration timestamp and applies the same receipt
gate. Template-originated work therefore cannot bypass P4.

## Task state schema compatibility

P4 advanced the Task state schema from v7 to **v8** because `TaskStep` began
persisting the optional TDD seam declaration and attested runs. P5 subsequently
advances the current Task schema to v9 for generic execution contracts; v8
remains a supported lazy-migration input.

The reader accepts schema v1 through v8. Schema v1-v7 tasks are upgraded to v8
in memory when loaded; no bulk rewrite is performed. A legacy task is persisted
as v8 only after a normal state mutation. This keeps production migration lazy
and rollback-friendly while preserving the P0-P3 dependency, context, quality,
diagnostic, handoff, and traceability fields introduced before P4.

The public `task_manage` contract must expose both
`intent_spec` and `engineering_policy` for `final_review`, as well as the
P4 `tdd_seam` receipt references. Contract-drift tests cover these fields so
the runtime schema cannot silently diverge from the Task state machine again.

## Trust boundary

P4 is now **EXECUTOR-ATTESTED / ORDERED / SINGLE-USE** inside the AgentDock
runtime boundary.

The receipt SHA-256 detects accidental or out-of-band file changes but is not a
secret-key signature. A host administrator or process with unrestricted write
access to AgentDock state remains outside this contract's threat model.
Filesystem permissions, service identity, container/host isolation, and normal
deployment controls remain the security boundary.

## Verification

P4 acceptance requires:

- unit tests for receipt issue/resolve/claim and rollback;
- command/session tests proving completed executions emit receipts;
- negative Task tests for forged, stale, out-of-order, reused, timed-out, or
  killed evidence;
- Task/Workflow propagation tests;
- targeted regression across Task, command, app, and MCP contracts;
- full repository regression in an environment with the repository's required
  shell/git tools and non-root permission semantics.

Source-level acceptance does not by itself perform a production deployment.
